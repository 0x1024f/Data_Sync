# Data Sync Agent 项目说明

适用版本：源码声明版本 0.1.0；按 2026-09-28 当前工作区实现整理。

## 1. 项目用途

Data Sync Agent 是部署在 Windows 数据源机器上的单向数据上传程序。它定时扫描指定目录，在文件稳定后上传到一个或多个 MinIO 对象存储；也可以轮询符合条件的 MySQL 表，将新增记录作为批次上传到对象存储。

适用于业务文件汇集、多站点数据分发、数据库新增记录归档等场景。程序提供命令行和 Windows 服务两种运行方式，没有图形界面。

## 2. 功能与处理流程

### 目录文件

1. 根据 `root`、`include`、`exclude` 扫描目录，排除规则优先。
2. 文件大小和修改时间连续保持不变达到 `stable_seconds` 后，生成本地快照。
3. 在 SQLite 中记录文件版本及各目标上传任务，各目标独立执行和重试。
4. 按相对源目录的路径写入 MinIO。后续内容发生变化时覆盖同一路径对象；内容摘要相同则不重复上传。

例如：源目录为 `E:/business/data`，文件为 `E:/business/data/2026/09/a.hdf`，远端对象名就是 `2026/09/a.hdf`。文件上传不添加来源、日期或批次前缀，不使用 `targets.prefix`，也不生成 manifest。

首次扫描有两种模式：`new_only` 默认只记录现有文件基线，此后新增或修改才上传；`existing_and_new` 同时采集现有文件。基线保存在工作目录中，重启后保留。

### MySQL 新增记录

按主键游标轮询、分页生成批次，将数据文件和 manifest 上传到各目标，manifest 最后提交。支持采集游标持久化和中断恢复。

启用前必须确认记录按游标顺序提交，并显式设置 `commit_order_guaranteed: true`。只有 AUTO_INCREMENT 不能保证这一条件；并发事务可能导致漏采。该模式不采集已有行的更新或删除，也不直接写入对端数据库。需要入库时，由接收端另行实现 manifest 消费程序及幂等处理。

### 可靠性与运行管理

- 使用本地 SQLite 保存任务、游标和上传状态，重启后恢复。
- 支持大文件分片上传及恢复；网络类故障按退避策略重试。
- 同一目标的同一文件对象按版本顺序执行，旧版本阻塞时后续版本等待；其他对象和目标可继续。
- 提供配置校验、状态查询、手动重试、结构化滚动日志。
- 支持 HTTP 直连，或 HTTPS 域名连接；可结合 HAProxy 按 TLS SNI 路由到不同目标。（若后期需支持上传其他地市需配置不同地市使用不同域名）

## 3. 范围与限制

- 属于单向上传，不是双向目录镜像。本地文件删除不会删除远端对象，源文件上传后保留。
- 文件覆盖使用同一对象名；不要将其视为远端历史版本备份系统。
- 不同源目录保留相对路径，可能产生同名对象冲突；同一 Agent 会阻止已检测到的跨源键冲突。不同工作目录或机器之间没有共享锁，不应写入同一对象键。
- 工作目录中的 spool 快照不会自动清理，需要监控磁盘容量。
- 文件稳定依据大小和修改时间，不是业务完成信号；稳定等待时间应大于业务写入中可能出现的暂停。

## 4. 技术与代码结构

源码要求 Python 3.9+；Windows 构建建议 Python 3.11/3.12，构建机器与交付系统架构保持一致。

| 路径 | 职责 |
| --- | --- |
| `data_sync/config.py` | YAML 配置校验、路径与凭据解析 |
| `data_sync/files.py` | 文件扫描、稳定性判断和快照采集 |
| `data_sync/mysql.py` | MySQL 增量采集与游标处理 |
| `data_sync/state.py` | SQLite 状态、任务与版本管理 |
| `data_sync/transport.py` | MinIO 上传、分片及重试处理 |
| `data_sync/runtime.py` | 运行循环、工作线程、进程锁和日志 |
| `data_sync/cli.py` | 命令行入口 |
| `data_sync/windows_service.py` | Windows 服务入口 |
| `deploy/windows/` | 构建、安装、卸载脚本 |
| `deploy/haproxy/` | HTTPS SNI 转发部署示例 |
| `tests/` | 自动化测试 |
| `config.example.yaml` | 通用配置模板 |

主要依赖：Pydantic、PyYAML、boto3、PyMySQL；Windows 服务和打包使用 pywin32、PyInstaller。

## 5. 开发与构建

在项目根目录运行：

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install '.[windows,test]'
python -m pytest -q
python -m data_sync --config config.example.yaml validate
```

模板中的占位密钥非空，因此 `validate` 可以通过，但这不代表能连接目标。开发运行前复制模板并填写实际配置。

在 Windows 上构建：

```powershell
powershell -File .\deploy\windows\build.ps1
```

脚本安装依赖、运行测试，随后生成 `dist/data-sync/` 和 `dist/data-sync-service/`。这是目录式打包，必须连同各自的 `_internal` 完整交付，不能只复制 EXE。接收方正常使用打包程序不需要安装 Python。

## 6. 交付内容与检查

建议交付包根目录包含：

```text
DataSync-delivery/
  data-sync/                    完整命令行程序目录
  data-sync-service/            完整服务程序目录及 config.example.yaml
  install.ps1                   来自 deploy/windows
  uninstall.ps1                 来自 deploy/windows
  项目说明.md
  打包后使用手册.md
```

构建脚本只生成两个程序目录，并把配置模板复制到服务目录；上述脚本和文档需要额外放入交付包。使用手册中的命令按该目录布局编写。

交付前：

1. 从准备交付的源码重新构建，记录源码版本、构建日期及测试结果。
2. 检查程序目录是否混入现场 `config.yaml`、真实密钥、私钥、运行状态或业务数据。只携带通用模板；需要 CA 时仅附接收方应使用的 CA 公共证书。
3. 不把 `.venv`、`build`、`.git`、`config.local.yaml`、现场测试配置或工作目录当作运行必需内容发送。
4. 在目标环境按使用手册完成文件上传、覆盖、重启恢复及服务运行验收。
