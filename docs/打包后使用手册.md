# Data Sync Agent 打包后使用手册

适用对象：收到 Windows 程序包的部署与运维人员。按 2026-09-28 当前源码行为编写。

2026-10-08 新增：目录文件上传成功后可通知业务接口，参见[通知配置说明](upload-notification.md)。使用此功能须从包含该功能的源码重新打包；已有 EXE 不会随源码修改自动更新。

## 1. 准备环境

- 使用与构建产物架构匹配的 Windows 系统；正式使用前在实际系统验收。
- 解压完整程序包，保留 EXE 同目录下的 `_internal`。无需另装 Python。
- 准备可读取的源目录，以及有足够空间、可读写的本地工作目录。
- 获取 MinIO API 地址、协议、端口、已创建的桶名和访问密钥。不要填写 Web 控制台地址。
- 确认当前机器到目标端口可达；HTTPS 还需正确的域名解析和受信任证书。
- 安装 Windows 服务需要管理员权限，普通前台运行只需相关目录和网络权限。

本文假设将交付包解压到 `C:\DataSync`，内容如下。如果实际路径不同，请统一替换示例命令路径。

```text
C:\DataSync\
  data-sync\
    data-sync.exe
    _internal\
  data-sync-service\
    data-sync-service.exe
    _internal\
    config.example.yaml
  install.ps1
  uninstall.ps1
  项目说明.md
  打包后使用手册.md
```

## 2. 创建配置

打开 PowerShell：

```powershell
Set-Location C:\DataSync
Copy-Item .\data-sync-service\config.example.yaml .\data-sync-service\config.yaml
notepad .\data-sync-service\config.yaml
```

复制命令只在首次创建时执行，已有配置时直接编辑，避免覆盖现场参数。服务固定读取服务 EXE 同目录的 `config.yaml`；命令行也必须指向这份文件。

以下是一份仅同步文件的完整 HTTP 示例，可替换配置内容后按现场修改。示例地址是占位地址，不能直接使用。

```yaml
agent:
  source_id: station-001
  work_dir: C:/DataSync/runtime
  scan_seconds: 10
  min_free_bytes: 1073741824
  log_level: INFO

files:
  - id: business-files
    system: BUSINESS
    root: E:/business/data
    include: ['**/*']
    exclude: ['**/*.tmp', '**/*.part', '**/*.done']
    recursive: true
    initial_scan: new_only
    stable_seconds: 60

mysql: []

targets:
  - id: site-a
    enabled: true
    scheme: http
    host: 192.0.2.10
    port: 9000
    bucket: business-data
    access_key: 'REPLACE_WITH_ACCESS_KEY'
    secret_key: 'REPLACE_WITH_SECRET_KEY'
    concurrency: 2
    timeout_seconds: 60
```

YAML 使用空格缩进，不能使用 Tab。路径建议使用 `/`；密钥使用引号包裹。相对路径一律相对于配置文件所在目录，而非终端当前目录。

| 配置项 | 填写说明 |
| --- | --- |
| `source_id` | 本机采集实例标识，使用字母、数字、下划线或连字符 |
| `work_dir` | 持久化状态、快照和日志目录，不能放在被扫描目录内部 |
| `scan_seconds` | 扫描间隔，单位秒 |
| `min_free_bytes` | 新采集所需的可用空间门槛，示例为 1 GiB；不是缓存上限 |
| `files[].id` | 文件源唯一标识；多个文件源不可重复 |
| `system` | 业务系统标识，不会自动添加到远端文件路径 |
| `root` | 实际需要扫描的目录 |
| `include` / `exclude` | 文件匹配和排除规则；例如只采集 HDF/XML 可用 `['**/*.hdf', '**/*.xml']` |
| `recursive` | 是否扫描子目录 |
| `initial_scan` | `new_only` 仅基线后新增或修改；`existing_and_new` 首次也采集现有文件 |
| `stable_seconds` | 文件大小、修改时间持续不变的等待时间 |
| `targets[].id` | 目标唯一标识，投入使用后不要随意修改 |
| `host` | 仅主机名或 HTTP IP，不包含协议、端口、桶名或路径 |
| `port` / `bucket` | MinIO API 端口及预先创建的桶名 |
| `access_key` / `secret_key` | 有该桶相应权限的访问凭据 |

**首次扫描模式应在第一次运行前确定。** 已经建立基线后，修改为 `existing_and_new` 不应被当作历史补传开关；需要补采时应先停止程序，保留原状态并制定重新采集方案。

### HTTPS 配置

将目标的协议、主机和端口替换为实际值。例如：

```yaml
    scheme: https
    host: minio.example.internal
    port: 443
    ca_bundle: C:/DataSync/certificates/internal-ca.pem
```

当前实现要求 HTTPS 使用包含点号的域名，不接受 IP。证书需覆盖该域名。使用受信任的公共证书时可省略 `ca_bundle`；使用内部 CA 时提供 CA 证书文件。HTTP 不得配置 `ca_bundle`，且传输不加密，应在可信网络使用。

### 凭据与多个目标

MinIO 支持直接填写密钥，也支持 `access_key: env:SYNC_ACCESS_KEY`、`secret_key: env:SYNC_SECRET_KEY`。程序不自动读取 `.env`。服务模式下必须让服务账户获得环境变量；终端中的临时 `$env:...` 不会自动传给 Windows 服务。

在 `targets` 下增加配置块可以上传到多个目标，使用不同 `id`。新目标不自动补传已有历史文件版本。已使用的目标改变协议、地址、端口、桶或前缀时，应使用新目标 ID 并重新规划采集范围。

多个源文件的远端路径均相对于各自 `root`，不会自动按源 ID 隔离。请规划相对路径避免冲突。文件不使用 `targets.prefix`，不要依靠此参数隔离文件。

## 3. 首次运行与验证

### 第一步：检查配置

```powershell
& C:\DataSync\data-sync\data-sync.exe --config C:\DataSync\data-sync-service\config.yaml validate
```

成功输出 `Configuration and secret references valid`。此命令只校验配置、凭据引用和所配置目标 CA 文件是否存在，**不验证远端连接、桶或权限，也不证明已上传成功**。

### 第二步：前台持续运行

```powershell
& C:\DataSync\data-sync\data-sync.exe --config C:\DataSync\data-sync-service\config.yaml run
```

终端保持运行，用 `Ctrl+C` 正常停止。程序主要写文件日志，终端无持续输出不代表停止。

首次测试建议使用独立测试目录和测试桶。采用 `new_only` 时，先让目录完成首次扫描，再新建一个符合筛选条件的小文件；如扫描报错，先修复错误。等待稳定窗口、扫描调度及上传完成，实际耗时不等于固定的 60 秒。

### 第三步：查看状态和远端文件

另开 PowerShell：

```powershell
& C:\DataSync\data-sync\data-sync.exe --config C:\DataSync\data-sync-service\config.yaml status
Get-Content C:\DataSync\runtime\logs\agent.jsonl -Tail 50
```

检查 `tasks` 中对应目标的 `COMMITTED` 数量，并在 MinIO 查看实际文件。例如 `E:/business/data/sub/a.txt` 应上传为 `sub/a.txt`，没有额外前缀或 manifest。首次运行前查询 `status` 会失败，因为尚未初始化状态数据库。

再修改测试文件，等待稳定后确认远端同名对象更新。下载远端文件并与本地最终文件比较 SHA-256，确认内容一致。可用 `Get-FileHash -Algorithm SHA256 文件路径` 计算摘要。不要只凭进程存在或校验命令成功判断同步完成。

`once` 仅扫描一轮并尝试当前可执行任务，不会等待整个稳定窗口，不适合替代上述首次测试：

```powershell
& C:\DataSync\data-sync\data-sync.exe --config C:\DataSync\data-sync-service\config.yaml once
```

## 4. 安装为 Windows 后台服务

先用 `Ctrl+C` 停止前台程序。不要让服务和 `run`/`once` 同时使用同一工作目录。以管理员身份打开 PowerShell：

```powershell
powershell -File C:\DataSync\install.ps1 -ServiceDirectory C:\DataSync\data-sync-service
```

脚本注册 `DataSyncAgent`，设置自动启动及异常恢复，但不会立即启动。若组织策略阻止脚本执行，请按本机管理规定处理。

打开 `services.msc`，找到显示名 `Data Sync Agent`，在“登录”页配置合适的服务账户，确保该账户：

- 能读取源目录、配置和 CA 文件；能读写整个 `work_dir`。
- 能访问目标网络并读取所需环境变量。
- 如果源在网络共享上，拥有对应共享及文件权限；不要依赖交互登录用户的映射盘符。

随后启动并检查：

```powershell
Start-Service DataSyncAgent
Get-Service DataSyncAgent
& C:\DataSync\data-sync\data-sync.exe --config C:\DataSync\data-sync-service\config.yaml status
```

状态显示 Running 后仍需检查日志和真实上传结果。服务启动失败时，检查 Windows 事件查看器中的应用程序日志、服务目录 `config.yaml` 及账户权限。

## 5. 日常操作

```powershell
# 停止，等待正常退出后再维护
Stop-Service DataSyncAgent

# 修改配置后重新启动（运行中不自动重载配置）
Start-Service DataSyncAgent

# 查询服务与上传状态
Get-Service DataSyncAgent
& C:\DataSync\data-sync\data-sync.exe --config C:\DataSync\data-sync-service\config.yaml status
```

`status` 可在运行中使用。输出中 `tasks` 是目标任务状态统计，`file_versions` 是文件版本统计，`batches` 是 MySQL 批次统计，`file_errors` 是文件错误，`checkpoints` 是采集游标，`runtime` 含心跳和源采集错误。心跳是 Unix 时间戳，单次存在心跳不代表当前仍在运行。

日志位于 `<work_dir>/logs/agent.jsonl`，单文件达到 10 MiB 后滚动，保留 5 份备份。工作目录还含 `state.sqlite3` 和 spool 快照，不能作为普通临时文件随意删除。

## 6. 常见问题

| 现象 | 处理方法 |
| --- | --- |
| 老文件没有上传 | 检查是否使用 `new_only`；默认行为是先建立基线，不上传已有文件 |
| 新文件没有上传 | 检查筛选规则、源目录权限、是否持续写入、稳定窗口、目标是否启用，以及剩余磁盘空间 |
| `RETRY_WAIT` | 检查网络、MinIO 和磁盘等错误原因；可重试故障恢复后会自动重试 |
| `BLOCKED` | 检查日志中的任务号和错误类型，修复证书、权限或配置，再停止程序并手动重试 |
| `ObjectKeyConflict` | 不同来源占用同一对象路径；重新规划目录或桶，单纯重试不能解决路径冲突 |
| `SOURCE_MISSING` | 恢复源文件，等待后续扫描及稳定窗口 |
| `configuration_invalid` | 按输出中的字段位置检查 YAML、字段名和类型；未知字段也会被拒绝 |
| `status` 返回 `ValueError` | 尚未初始化时会出现；也应确认所用配置和工作目录是否正确 |
| 启动返回 `RuntimeError` | 一种可能是同一工作目录已有进程；检查前台程序、服务及日志，不要直接删锁文件或状态库 |
| 前台正常、服务失败 | 检查服务账户的文件权限、环境变量和网络共享权限 |
| 磁盘持续增长 | spool 不自动清理，及时扩容或按经确认的运维方案清理，不要整体删除工作目录 |
| 本地删了文件，远端还在 | 这是预期行为，不同步删除操作 |

手动重试示例，`123` 必须替换为实际任务 ID，且先修复原因：

```powershell
Stop-Service DataSyncAgent
& C:\DataSync\data-sync\data-sync.exe --config C:\DataSync\data-sync-service\config.yaml retry 123
Start-Service DataSyncAgent
```

前台运行时改为先 `Ctrl+C` 停止，重试后再 `run`。任务 ID 可从含 `task` 字段的错误日志获取；`status` 仅给任务聚合数量，不列出所有任务 ID。没有日志任务号时应交由维护人员只读检查状态库，不要自行修改 SQLite。`retry` 仅接受 `BLOCKED` 或 `RETRY_WAIT` 任务。

账号权限通常需要对应对象路径的 PutObject、GetObject（用于 HEAD）、AbortMultipartUpload、ListMultipartUploadParts，以及合适范围的 ListBucket。文件按相对路径直接写入，只授权 `transfer/` 前缀可能导致失败。

## 7. 升级、备份与卸载

升级流程：停止服务并确认进程退出 → 备份配置及完整工作目录 → 替换完整程序目录（包括 `_internal`）→ 恢复服务目录的 `config.yaml` → 校验配置 → 启动并检查状态与上传。

备份应包含完整 SQLite 状态及可能存在的 WAL 文件、spool 和相关配置。程序仍在运行时不要仅复制一个 SQLite 文件作为完整备份。保留原 `work_dir` 路径，避免把运行状态误当作程序文件覆盖。不能用旧程序写入新版状态库。

从旧“文件分组上传”版本升级属于特殊情况：新程序拒绝旧分组状态，需保留旧工作目录并使用新的工作目录；旧未完成任务不会自动迁移，应由维护人员单独制定方案。

卸载服务（管理员 PowerShell）：

```powershell
powershell -File C:\DataSync\uninstall.ps1 -ServiceDirectory C:\DataSync\data-sync-service
```

脚本停止并移除服务，保留配置、日志和状态；不会删除源文件或 MinIO 对象。
